# QA-UI-003: constrained process framing inside Demo3's room

Source decision note, 2026-10-23. No application change, UI input, engine/headless launch or private camera query. [Seven-original native review](demo3-frame-process-visibility-review.md) establishes the repeated actual1021×660 Engineering visibility failure and working Immersive alternative. The candidate below is not implemented or verified native behavior.

## Geometry materially narrows the hypothesis

Demo3 is an intentional **closed room**, not the ordinary environment cutaway. [PROJECT_INFORMATION.md](../../../PROJECT_INFORMATION.md),1324–1333 and1391–1402 records the prior requirement for a connected material-source volume, no visible wall top/end/sky, and four full-height enclosing boundaries. Removing that enclosure globally would reverse accepted presentation work.

The actual builder is [DemoEnvironmentPresentation.RemainingProductionNine.cs](../../src/App/DemoEnvironmentPresentation.RemainingProductionNine.cs),17–61, kind9, selected by the exact `pusher-open-takeaway-side` art direction. It runs before the older generic layout switch (ArtDirections26–29); that older switch's open-side comment does **not** describe this resulting room.

- Its reserve starts from actual protected process bounds and merges the operator-access bounds. Then `w=max(8,reserve.Size.X+4.6)`, `dep=max(6,reserve.Size.Z+4.6)` and height7.5. No runtime copy of these final camera limits is currently published.
- Rear planes are at `c.X+sx*w/2` and `c.Z+sz*dep/2`. Actual camera-side wall centers are `c.X-sx*(w/2+15)` and `c.Z-sz*(dep/2+15)`, thickness.18. Continuous ceiling bottom is7.5; foundation and roof extend36 beyond nominal width/depth. The comments explicitly assume the closing walls remain beyond the **normal** lesson camera.
- Side and rear walls extend an additional30 (lines87–89,186–187). Thus a camera can leave a finite interior even though the initial machinery envelope is clear.
- Both the scene's authored direction `(10.8,6,10.8)` and Demo3's profile `(8.8,.72,5.2)` have positiveX/Z. Environment rear signs are therefore `sx=sz=-1` (DemoEnvironmentPresentation.cs55–58). A mismatch between authored and profile *signs* is contradicted by source; both approach from the same quadrant.
- The separate [material-entry volume](../../src/Scenes/SceneComposer.MaterialEntryPortal.cs),23–31,78–143 is inside the process composition. Demo3 authors it at X−2.6 with depth10 toward negativeX, cross-span32 and height7.5 (scene JSON501–511). Its real ceiling/returns/rear wall must remain intact. Unlike this volume, generated environment geometry is a sibling, deliberately excluded from process framing/picking/persistence (DemoEnvironmentPresentation.cs7–10; Main.DemoEnvironment.cs80–93).

[FrameComposition](../../src/App/Main.cs),4611–4626 keeps only selected process equipment plus the integrated control installation and applies35° FOV/low direction. Main4731–4744 then backs away in inverse proportion to the actual usable aperture, with no enclosing-room constraint. The saved Engineering image has an approximately370-pixel-wide opening (x331..700), with full original width1021. A finite wall reserve that works in the broad view need not contain that farther eye. The nearly level direction keeps the eye below the7.5m ceiling over a substantial distance, so crossing a camera-side wall can plausibly fill the entire opening with one surface.

This is a stronger source explanation than a missing model or fixed UI overlay: the same machinery appears in Immersive, and Whole Scene changes the central rendering without changing the docks. It still does **not** identify the actual blocking mesh or expose actual native camera coordinates.

## Minimum principled candidate

Use a **Demo3-only, Frame Process constrained fit with an adaptive lens**, keeping the current direction, focus set and nominal35° unchanged whenever the ordinary fit is inside the authored room. This preserves the already working Immersive presentation when it does not need adaptation. Do not make it a general camera collision controller.

1. The room builder should publish a proposed presentation-only set of interior camera planes derived from the **same reserve/c/w/dep/h and wall thickness** it uses to construct kind9. This would be new metadata/property, not an existing API. Main must transform it in the same coordinate frame as the candidate camera; do not compare world eye to local bounds or hard-code a guessed24m distance. Include ceiling/floor and the physical camera offsets/near clearance.
2. Main's explicit process-framing path should keep the ordinary solution if valid. Otherwise select an eye along the same intended view ray that stays inside those planes and solve a wider FOV that fits **every selected transformed corner** inside the actual aperture. For a point with view depth `q>0`, required angle depends on its own lateral extent divided by `q`, not a blanket `.22*halfDepth` allowance. Use the actual Godot projection to validate the final result. Existing code already uses `UnprojectPosition`/`IsPositionBehind` for these checks; no new projection API is needed.
3. Both interior containment and full projection fit must pass. A clamp with the old lens, a wall-only camera-center test, or an unchecked enlarged FOV is insufficient. Screen fit also does not imply every originally designed occluded surface is visible: retain the authored infeed portal and normal machinery occlusion; acceptance needs the main carrying path, measurement station, pusher, side receiver and operator cabinet useful in the image.
4. Keep the adjusted lens owned by this automatic presentation result. Restore the nominal lens on return to the broad working view and prevent carryover into Frame Whole Scene, another scene, asset previews or visual-review cameras. Whole currently skips the profile assignment, so an adaptive FOV would otherwise silently leak through that command. If a bounded acceptable lens/pose solution cannot fit, report that failure during verification rather than silently cropping equipment or removing architecture.
5. Call `CaptureCurrentView` once with the final target/pose/lens, preserving its target/distance/yaw/pitch bookkeeping. Recompute only on existing explicit Frame Process or actual aperture/layout changes. Manual RMB orbit, MMB pan and wheel remain owned by [SceneCameraController.cs](../../src/App/SceneCameraController.cs),28–57,89–140; do not auto-snap every render frame or add a new orbit wall clamp under this issue.

A conditional higher camera pitch is a poorer first candidate: it changes the accepted operator sightline, risks the continuous ceiling, and can move cabinet legends behind equipment. Selectively hiding walls is also not the first candidate because no current engineering cutaway contract supersedes the explicitly closed-room requirement. A future deliberate cutaway feature would need separate ownership/restoration semantics; it should not be smuggled into this repair.

## Finite regression obligations

- **Exact failing native context:** actual1021×660 Engineering → Frame Process, settled and repeated. The machinery/cabinet must render usefully inside the true central aperture; a nonempty viewport or projected target alone is inadequate. Retain camera/plant state boundaries and actual wall/roof appearance. Do not infer logical viewport or interface percentage from native pixel width alone; SceneViewportRect uses the real settled dock geometry and DesktopUiScalePolicy can scale it.
- **Working context and navigation:** same scene in its existing Immersive view, Operator Console and Scenario+Ladder Split; one return to Engineering and one diagnostics/aperture change. Check the working broad framing returns, lens does not drift, and explicit Whole Scene does not inherit the adaptive Process lens. Whole may legitimately inspect architecture; it is not required to become another process view.
- **Manual ownership/picking:** one ordinary wheel zoom, MMB pan and RMB orbit in the3D region remain effective; UI clicks/scrolls outside it must not move the camera. A known visible physical control must still pick at its actual displayed position after adapted framing. No new plant behavior or unsafe input injection is needed.
- **Local geometry/projection regression:** actual composed focus corners and actual room planes, including nonzero offsets, must satisfy projection/depth/containment together. Keep plant transforms and runtime points unchanged by framing. Then check the existing1600×900 baseline once; conditional adaptation must not degrade a fit that already works. If common code is changed, a neighboring profiled scene plus asset/visual-review path checks lens state leakage; do not create a77-scene framing crossproduct.

Existing [environment review](../../src/App/Main.EnvironmentReview.cs),37–77 checks sibling ownership, protected-envelope separation and clear door apertures; it never proves a camera can see the process. The split-shell check Main2137–2142 tests target centering, which can pass behind an opaque wall. Existing process/curriculum logic checks likewise do not qualify this view route. Native before/after visibility and interaction therefore remain necessary even if all those existing checks pass.

No repair is selected for implementation here. The preferred candidate is a small isolated presentation change for the later implementation stage; actual feasibility, acceptable lens and native regression results remain unverified.
