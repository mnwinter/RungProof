## QA-UI-002: preserve action history while publishing successful Run

The earlier causal note already establishes the two status-label owners and the missing successful outer publication. The additional concrete trap is **event history**: `SetWorkspaceStatus` always records an operator event (`SimulatorShell.cs:23893–23917`) and the list keeps only 32 entries. Calling it from every `UpdateVirtualController` snapshot would both overwrite fresh ACTION ACCEPTED/BLOCKED text and quickly evict the native Health acknowledgements now used by Q21. Controller-state transitions already log separately at 21164–21165.

The narrow practical candidate remains one explicit outer status publication per successful ordinary local App Run, after actual Run and its existing drive/E-stop/draft gates. `VirtualControllerSession.Run:92–98` sets runtime state and synchronously publishes its lifecycle snapshot; it does not prove a first accepted logic scan or mechanical motion. Appropriate wording can report offline runtime running/current draft loaded, without claiming that a machine Start occurred, that a mechanism moved, or that an external PLC is connected. Keep Verify+Load's valid/loaded outcome distinct from Run (`SimulatorShell.cs:18904–18926`). There is no need for a global status view-model rewrite to close this seam.

| Minimum obligation | Specific failure it prevents |
| --- | --- |
| Extend the existing exact App Run diagnostic recovery check to the **outer** label and its error color; exercise both same already-loaded draft and edited valid draft. | Existing `AuditDiagnosticsReview:32–35` tests inner `_ladderWorkspaceStatus`; another editor check at `SimulatorShell.cs:22054–22057` tests Error List/summary only. Either can pass with stale outer RUN BLOCKED. |
| Invalid current draft with an older loaded program, E-stop/drive blocked Run and external readiness retain the correct blocked outcome. Verify+Load while stopped says loaded/verified rather than running. | A successful compile, older running snapshot or common publisher must not supersede an authoritative gate. |
| After one successful Run, subsequent snapshots preserve a fresh operator-action footer and do not add an outer Run event each scan. Existing old rejection remains in Health as history. | Avoid acknowledgement loss, log flooding and destructive history clearing. |
| Repeat the already documented blank Run → actual authoring → valid App Run native route after a future repair. | Label automation alone cannot close the visible repro. |

Watch-only metadata must retain the current execution identity and memory, as already required by `Main.cs:1604–1607` and the existing note. Do not reload/reset the controller merely to refresh text. A category/identity-aware status object is an optional broader design if sticky unrelated-error ownership is later required; it is not necessary to repair one explicit successful Run publication.

## QA-SPEC-002: retain proven toggle behavior, clarify the lesson

Both affected source scenes declare toggle actions and stable symbolic bindings: Lab 2.1 `toggle-material-call` → `material_call_pressed`; Lab 2.6 `toggle-request` → `request_held`. Their purpose/guide prose instead says held or spring-return (`lab-2-01-workstation-call.scene.json:6,114,124,127,147`; `lab-2-06-ready-attention.scene.json:6,145,155,158,178`). The existing native reports prove maintained state after mouse-up and a second click clearing it. That behavior is not a new controller failure.

The smallest coherent repair candidate is wording-only: explicitly state that one click sets the maintained symbolic request, a second click clears it, and releasing the mouse does not clear it. An action label such as “Toggle request ON/OFF (maintained)” removes the ambiguous “Press / release.” Keep action IDs, point/binding names, type=toggle, PC/PLC ownership, initial values, truth logic and geometry unchanged. The physical cap's brief spring-back animation does not define the logical input lifetime: accepted feedback is a 0.28 s animation (`SceneControlInteractor.cs:48–110`), while Main's scene dispatch handles left **press** events (`Main.cs:5099–5105,5141–5148`).

Changing a shared mouse-release handler would alter already proven maintained controls and require pointer-capture, outside-aperture release, focus loss, scene change and pause/Stop policies. A one-scan pulse would also fail to represent a held input. Neither is a wording repair. Renaming `request_held` or `material_call_pressed` would unnecessarily break saved projects; explain their maintained simulator meaning instead.

**Documentation synchronization trap:** `generate_help_documents.py --sync-scene-io` intentionally preserves authored prose and non-I/O sections (250–268), so it will not fix these contradictions. Full generation rewrites all asset/scene help and the index (279–300). The existing `scene_help(scene, entry)` renderer can render just the two documents (111–172); a read-only comparison confirmed both current files match it exactly, ignoring trailing whitespace, and their catalog entries have no duplicate description field. A future narrow correction can therefore update the two source scenes' presentation prose/action labels and render only those two help files without losing current authored additions or touching the wider catalog. Review the resulting diff.

Existing help validation checks declared I/O rows (`validate_help_documents.py:57–78`), and sync tests intentionally preserve prose; neither establishes semantic agreement between held wording and toggle behavior. The control-installation verifier calls ExecuteAction twice and labels the second call “release” (`Main.ControlInstallationReview.cs:522–529`); it does not test physical mouse-up semantics. Minimum verification for a wording-only change is unchanged non-presentation scene contract plus reviewed visible description/guide/action wording and the two rendered help files. Reuse the existing native toggle evidence; no new all-scene or release-state test matrix is justified unless behavior itself changes.
